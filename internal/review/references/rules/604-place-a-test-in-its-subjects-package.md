# 604: Place a Test in Its Subject's Module and Package

A test belongs with the class it tests on two axes, and both must match:

1. **Module.** The test lives in the `-test` module that pairs with the subject class's module — a test for a class in the `layout` modules belongs in `layout-test`, not in some other feature's test module that merely happens to depend on it. When a sibling test for a class in the same subject module already exists, follow its precedent: put the new test alongside it, in the same module.
2. **Package.** A unit test lives in the same package as its subject, with a `Test` suffix: `com.liferay.foo.Bar` has its unit test at `com.liferay.foo.BarTest` in `src/test/java`. An integration test lives in the subject's package with a trailing `.test` subpackage: `com.liferay.foo.test.BarTest` in `src/testIntegration/java`.

**Rationale:** Matching the test's module and package to the subject's makes the pair findable from either side — `git ls-files` returns them next to each other, and the IDE jumps from the class to its test without a lookup. A unit test in the same package can exercise package private members; an integration test sits one level deeper under `.test` because it lives in a separate test module and the suffix avoids colliding with same named classes in the subject module. Placing a test in a foreign feature's `-test` module scatters the suite and hides it from the next person who edits the subject class.

A violation is a test whose module or package does not match the subject's, even when the test compiles and runs correctly: the same `Test` suffix but a different package root (`com.liferay.oauth.client.persistence.*` for a class in `com.liferay.portal.security.sso.openid.connect.*`), or a test dropped into an unrelated feature's `-test` module (a constraint-resolver test placed in `change-tracking-test` instead of `layout-test`) when a sibling test for the same subject module already sits elsewhere.

**Examples:** https://github.com/brianchandotcom/liferay-portal/pull/175571 — `OpenIdConnectProviderPortalInstanceLifecycleListener` lives in `com.liferay.portal.security.sso.openid.connect.internal.configuration.instance.lifecycle`, but the integration test was placed in `com.liferay.oauth.client.persistence.internal.configuration.instance.lifecycle.test`; the test's package should mirror the subject's. https://github.com/brianchandotcom/liferay-portal/pull/177350 — layout friendly-URL constraint-resolver tests (`LayoutConstraintResolverTest` and siblings) were placed in `change-tracking-test`; they belong in `layout-test`, following the existing precedent of `LayoutClassedModelUsageConstraintResolverTest`.
